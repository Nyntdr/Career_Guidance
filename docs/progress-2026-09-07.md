## 4. Resume ML subsystem (today's core work)

### 4.1 Architecture

```
resume (txt/pdf/docx)
   │  ResumeTextExtractor
   ▼
ResumeParser::segmentSections ──► ResumeSegmenter (hybrid)
   │                                    │
   │   deterministic tier                │  ML tier (when models ready)
   │   dictionary exact +                │  per-line RandomForest proba()
   │   canonical colon/case match        │  + K-Means cluster smoothing
   │                                    ▼
   └──────────────► Resume + ResumeSection rows
```

### 4.2 Files

| File | Role |
|---|---|
| `app/Services/ResumeParser.php` | Dictionary `HEADINGS` (23 keys → 13 section types), `parseAndStore`, `extractSkills`, `nextVersion` |
| `app/Services/Ml/ResumeSegmenter.php` | Hybrid sequencer: dictionary fast-path + ML switch gate + K-Means smoothing |
| `app/Services/Ml/ResumeLineVectorizer.php` | Feature builder: unigram/bigram/trigram vocab (cap 220) + 8 scalar features |
| `app/Services/Ml/SectionClassifier.php` | Predicts per-line label + score via RF `proba()` |
| `app/Services/Ml/SectionClusterer.php` | Predicts per-line cluster id via K-Means `predict()` |
| `app/Services/Ml/ModelRepository.php` | Persist/load models + vocab (Rubix `PersistentModel`/`Filesystem`) |
| `app/Console/Commands/MlTrain.php` | `ml:train` — trains RF + K-Means from corpus |
| `app/Console/Commands/MlDiagnose.php` | `ml:diagnose` — dict vs ML comparison across fixture resumes |
| `app/Services/ResumeTextExtractor.php` | PDF/DOCX/TXT text extraction |

### 4.3 Vectorization

- **Vocabulary:** `BASE_VOCAB` (72 heading-indicator words) merged with corpus-derived unigrams, bigrams, and trigrams (count ≥ 2, capped to 220 terms). Current stored vocab: **144 terms**.
- **Each line → vector:** TF per vocab term (capped at ℓ/3, phrases matched against the raw lowercased line) **+ 8 scalar features**: word count/8, capitalized ratio, all-caps flag, digit count/3, ends-with-colon, ends-with-period, avg word length/10, line length/80.

### 4.4 How the models were trained

Command: `php artisan ml:train [--model=all|classifier|clusterer] [--include-resumes]`

- **Corpus:** `database/ml/section_lines.json` (**v2 — 149 labeled line samples, 10,984 bytes**) across 13 labels: experience 23, skills 19, summary 15, certifications 11, volunteer 10, projects 10, education 12, contact 12, publications 8, awards 9, interests 8, references 6, languages 6. The command falls back to the shipped file (copies it into `storage/app/ml/training/`) and can additionally **harvest weak labels** from already-stored `resume_sections` (`--include-resumes`).
- **Random Forest:** Rubix `RandomForest` — **500 trees, bootstrap ratio 0.3**, CART base learner; trained on a 80/20 stratified holdout. Current persisted model: `storage/app/models/resume_section_classifier.model` (trained 07-Sep 05:22).
- **K-Means:** Rubix `KMeans(k = 6)`; model `resume_section_clusterer.model`.
- **Vocabulary:** `storage/app/ml/vocab.json` (144 terms).
- **Honest accuracy note:** holdout accuracy ≈ **20 %** — the RF is a weak, noisy signal on this small corpus. That is exactly why the structural gates in §4.5 carry the real precision.
- Runtime readiness is verified: `ModelRepository::isReady() == true`; live probe results in §4.6.

### 4.5 Tuning against 246 real resumes (today)

User-provided corpus: 224 DOCX (real candidates) + 24 category PDFs (one per industry) extracted to `tests/Fixtures/resumes/`. Diagnosis (`ml:diagnose`) drove the following changes to `ResumeSegmenter`:

| Guard | Effect |
|---|---|
| `default_confidence` 0.12 → **0.3** | real fuzzy headings (~0.34–0.51) clear; content bullets (~0.41) blocked below floor |
| **Blank-line isolation** (`prevIsBlank`) | heading must be preceded by a blank line (or be first line) |
| **`looksLikeContent` negatives** | reject bullet glyphs/dashes, any 4-digit year (`12/2015`), `client/employer/current company/project name/role:` prefixes, `Responsibilities:`/`duties`/`job|project description` |
| **Canonical colon-stripped dictionary match** | `SUMMARY:`, `TECHNICAL SKILLS:`, `Professional Experience:` now resolve deterministically (correct labels, no RF guess) |
| **Dictionary-anchored ML scope** | ML splits only in the lead-in `contact` region when the doc has dictionary headings; document-wide only when dictionary found nothing (`dict=[contact]`) |
| **Single-word headings** need all-caps or trailing colon | kills content lines like `Calendaring`, `Methodologies` |
| Retained | first-content-line buffer guard (names stay in `contact`) |

**Measured impact (246 fixtures):** files whose ML output differs from dictionary output dropped **197 → 148 → 93**; **153 files now identical** with ML on/off. Residual differences are almost all a single added `summary`/`skills` lead-in section; pathological `experience,skills,experience,…` alternation is gone (a couple of `dict=[contact]` edge cases remain, e.g. `deepika_dc`).

## 5. ATS scan flow (wired, ready)

Upload → `parseAndStore` (sections + extracted skills) → `POST /resumes/{resume}/scan` with `job_posting_id` → `AtsScanner`:

- **Keyword:** required skills 70 % + soft skills 30 % (name + alias word-boundary matching).
- **Structure:** presence of summary/experience/education/skills sections.
- **Formatting:** bullets (cap 8) 40 %, action verbs (cap 5) 30 %, quantified metrics (cap 3) 30 %.
- **Readability:** `Readability::gradeLevel()` → 100 − 5×grade-over-7 (floor 20 / ceiling 95).
- Weighted overall (defaults 50/15/15/20, overridable via `ats_weights` setting).
- Persists `AtsScan` + `AtsMatchedKeyword` rows + `AtsScanDetail` suggestions → `ats.show` results page (ownership-guarded).

**Verification status:** code-complete, data seeded (12 jobs / 61 required skills / 27 aliases), models ready. An end-to-end HTTP smoke run + automated round-trip test are still **to-do** (§6.3).
